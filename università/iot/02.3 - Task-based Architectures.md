## Slide 3 – TASK-BASED ARCHITECTURES

- Problem: complex embedded software modelling and design
	- need of proper approaches to decompose/modularise the behaviour and functionalities
- Approach: Task-based architectures
	- The behaviour of the embedded software is decomposed into a *set* of **concurrent tasks**
	- each task represents a specific well-defined confided unit of work/job to be done
	- the behaviour of *each* task can be described by a FSM
	- the global behaviour is the result of the execution and interaction of the concurrent FSMs

>> In pratica si passa da un'unica FSM "monolitica" a più FSM sincrone più piccole, ognuna con il proprio periodo, eseguite in modo (logicamente) concorrente. "confided" è probabilmente un refuso per "confined" (unità di lavoro circoscritta).

## Slide 4 – EXAMPLE: LED-SHOW

- LedShow example: 3 + 1 leds (p. 68, [PES])
	- One led: blinking with period: 500 ms
	- The other three leds: turn on/off in sequence, with a time interval of 500ms
- This could be modelled as a single task / FSM, however the modelling is much easier and simpler if we model it as the explicit composition of 2 tasks/FSM
	- single task/FSM version: much higher number of states and transitions

>> Con un'unica FSM servirebbe il **prodotto** degli stati: 2 (led on/off) × 3 (quale dei tre led è acceso) = 6 stati, con le relative transizioni. Con periodi diversi (es. 500 e 150 ms) la FSM unica diventa ancora più complessa, mentre con due task basta 2 + 3 = 5 stati. In generale gli stati crescono come prodotto, non come somma.

## Slide 6 – TASK DECOMPOSITION: ADVANTAGES

- **Modularity**
	- every task is an independent module
	- the "interface" of the module in this case is the set of input/output variables / objects that the task is using (as input/output)
		- these can be shared with other modules
- Advantages
	- reduced complexity of the single task vs. the global behaviour
	- easier debugging
	- reusability

---
## Slide 7 – TASK DECOMPOSITION: CHALLENGES

- Tasks are **concurrent**
	- their execution overlaps in time
	- conceptually each task has its own logical control flow
- Tasks may have *dependencies* that create interactions among tasks and that need to be properly managed
	- interaction and coordination mechanisms
	- in our case, typically based on shared variables/objects

>> "Overlaps in time" va inteso a livello logico: su un microcontrollore single-core i task non girano davvero in parallelo, ma i loro `tick` vengono eseguiti uno dopo l'altro (interleaving), dando l'illusione di flussi di controllo indipendenti.

## Slide 8 – IMPLEMENTING TASK-BASED ARCHITECTURES - FIRST

- Introducing an abstract base class **Task**
	- **init** method
		- to initialise the task, called once
	- **tick** method (equivalent to the "step" method in FSM)
		- encapsulating the behaviour of the task
		- called periodically (period p)
- Each concrete tasks is implemented by extending this class
- Task execution carried on by periodically calling the tick method from the main loop

>> Ogni `tick` esegue al più una transizione della FSM del task (legge lo stato corrente, fa l'azione, aggiorna lo stato) e poi ritorna subito: non deve mai bloccarsi con `delay` o attese attive, altrimenti blocca anche gli altri task.

## Slide 11 – LED-SHOW EXAMPLE IN ARDUINO: BLINK TASK

BlinkTask.h

```cpp
#ifndef __BLINKTASK__
#define __BLINKTASK__

#include "Task.h"
#include "Led.h"

class BlinkTask: public Task {

  int pin;
  Light* led;
  enum { ON, OFF} state;

public:

  BlinkTask(int pin);
  void init();
  void tick();
};

#endif
```

BlinkTask.cpp

```cpp
#include "BlinkTask.h"

BlinkTask::BlinkTask(int pin){
  this->pin = pin;
}

void BlinkTask::init(){
  led = new Led(pin);
  state = OFF;
}

void BlinkTask::tick(){
  switch (state){
    case OFF:
      led->switchOn();
      state = ON;
      break;
    case ON:
      led->switchOff();
      state = OFF;
      break;
  }
}
```

>> Il `tick` è la traduzione diretta della FSM BlinkLed: lo `switch` sullo stato corrente esegue l'azione della transizione e aggiorna lo stato. Il led è dichiarato come `Light*` (interfaccia) ma creato come `Led` (implementazione): così si può sostituire l'attuatore senza toccare il task (`Light` è definita nel `Light.h` incluso da `Led.h`).
>> Il led viene creato in `init()` e non nel costruttore: gli oggetti task sono variabili globali (slide 13), costruite prima di `setup()`, quando l'hardware non è ancora pronto per essere configurato (es. `pinMode`).

## Slide 12 – LED-SHOW EXAMPLE IN ARDUINO: THREE LEDS TASK

ThreeLedsTask.h

```cpp
#ifndef __THREELEDSTASK__
#define __THREELEDSTASK__

#include "Task.h"
#include "Led.h"

class ThreeLedsTask: public Task {

  int pin[3];
  Light* led[3];
  int state;

public:

  ThreeLedsTask(int pin0, int pin1,
                int pin2);
  void init();
  void tick();
};

#endif
```

ThreeLedsTask.cpp

```cpp
#include "ThreeLedsTask.h"

ThreeLedsTask::ThreeLedsTask(int pin0, int pin1,
                             int pin2){
  this->pin[0] = pin0;
  this->pin[1] = pin1;
  this->pin[2] = pin2;
}

void ThreeLedsTask::init(){
  for (int i = 0; i < 3; i++){
    led[i] = new Led(pin[i]);
  }
  state = 0;
}

void ThreeLedsTask::tick(){
  led[state]->switchOff();
  state = (state + 1) % 3;
  led[state]->switchOn();
}
```

>> Qui lo stato (0, 1, 2) è usato direttamente come indice del led acceso, quindi non serve uno `switch`: `(state + 1) % 3` realizza le transizioni T0 → T1 → T2 → T0.
>> Piccola incongruenza con la FSM della slide 5: `init()` mette `state = 0` (T0) ma **non accende** `led[0]`, mentre in T0 dovrebbe valere P3=1. Così per il primo periodo i tre led sono tutti spenti e al primo `tick` si spegne `led[0]` (già spento) e si accende `led[1]`: il led sul pin 3 si accende per la prima volta solo al terzo `tick` (verificato con g++ e stub). Basterebbe un `led[0]->switchOn()` in `init()`.

## Slide 13 – LED-SHOW EXAMPLE IN ARDUINO: MAIN LOOP

led-show.ino

```cpp
#include "Timer.h"
#include "BlinkTask.h"
#include "ThreeLedsTask.h"

Timer timer;

BlinkTask blinkTask(2);
ThreeLedsTask threeLedsTask(3,4,5);

void setup(){
  blinkTask.init();
  threeLedsTask.init();
  timer.setupPeriod(500);
}

void loop(){
  timer.waitForNextTick();
  blinkTask.tick();
  threeLedsTask.tick();
}
```

>> Funziona perché i due task hanno lo **stesso periodo** (500 ms): un unico timer scandisce entrambi e a ogni periodo si chiama il `tick` di tutti. Con periodi diversi questo schema non basta (slide 14).
>> Sequenza ottenuta: al 1° tick led 2 on, led 3 off / led 4 on; al 2° led 2 off, led 4 off / led 5 on; al 3° led 2 on, led 5 off / led 3 on; e così via. Il led che lampeggia resta acceso 500 ms e spento 500 ms (ciclo completo di 1 s).

## Slide 14 – MANAGING DIFFERENT PERIODS

- As soon as we want to manage tasks/FSMs with different periods, it is necessary:
	- to keep track of the specific period for each task
	- implement a task scheduling so that each task is called with its own period
- To this purpose, we implement a simple, multi-tasking **cooperative scheduler**

>> "Cooperativo" significa che lo scheduler non può interrompere un task: ogni `tick` deve terminare e restituire il controllo volontariamente. Se un `tick` dura troppo, ritarda tutti gli altri (problema dell'*overrun*, più avanti nel modulo).

---
## Slide 15 – SIMPLE COOPERATIVE SCHEDULER

- Scheduler
	- keeps track of a list of tasks to be executed

![[IOT23-s015-1.png|500]]

- Cooperative round-robin strategy
	- the scheduler has a period p equals to the *greatest common divisor* among the periods of the tasks
	- at each period p, it advances the execution of each tasks by calling its method tick
	- internally, it uses a timer to realise the periodic behaviour

>> Esempio: task con periodi 500 ms e 150 ms → periodo base p = MCD(500, 150) = 50 ms. Ogni 50 ms lo scheduler si sveglia e chiama `tick` solo sui task il cui periodo è trascorso (500 ms = 10 periodi base, 150 ms = 3 periodi base). Così ogni periodo di task è un multiplo esatto di p.
>> Nel diagramma `addTask` restituisce `void`, mentre nel codice (slide 16) restituisce `bool`; inoltre il diagramma non mostra gli attributi `basePeriod` e `timer`.

## Slide 16 – A SIMPLE SCHEDULER

Scheduler.h

```cpp
#ifndef __SCHEDULER__
#define __SCHEDULER__

#include "Timer.h"
#include "Task.h"

#define MAX_TASKS 10

class Scheduler {

  int basePeriod;
  int nTasks;
  Task* taskList[MAX_TASKS];
  Timer timer;

public:

  void init(int basePeriod);
  virtual bool addTask(Task* task);
  virtual void schedule();

};

#endif
```

Scheduler.cpp

```cpp
#include "Scheduler.h"

void Scheduler::init(int basePeriod){
  this->basePeriod = basePeriod;
  timer.setupPeriod(basePeriod);
  nTasks = 0;
}

bool Scheduler::addTask(Task* task){
  if (nTasks < MAX_TASKS-1){
    taskList[nTasks] = task;
    nTasks++;
    return true;
  } else {
    return false;
  }
}

void Scheduler::schedule(){
  timer.waitForNextTick();
  for (int i = 0; i < nTasks; i++){
    if (taskList[i]->updateAndCheckTime(basePeriod)){
      taskList[i]->tick();
    }
  }
}
```

>> `schedule()` va chiamato in `loop()`: aspetta il prossimo periodo base, poi scorre tutti i task e chiama `tick` solo su quelli "maturi" (round-robin, sempre nello stesso ordine di inserimento).
>> Errore off-by-one in `addTask`: con la condizione `nTasks < MAX_TASKS-1` si possono aggiungere al massimo **9** task e non 10, quindi l'ultima cella di `taskList` non viene mai usata (verificato con g++: su 12 `addTask` ne riescono 9). La condizione corretta è `nTasks < MAX_TASKS`.

## Slide 17 – CLASS TASK REVISITED

```cpp
#ifndef __TASK__
#define __TASK__

class Task {
  int myPeriod;
  int timeElapsed;

public:
  virtual void init(int period){
    myPeriod = period;
    timeElapsed = 0;
  }

  virtual void tick() = 0;

  bool updateAndCheckTime(int basePeriod){
    timeElapsed += basePeriod;
    if (timeElapsed >= myPeriod){
      timeElapsed = 0;
      return true;
    } else {
      return false;
    }
  }

};
#endif
```

>> Ora ogni task conosce il proprio periodo: `init(int period)` non è più astratto ma memorizza il periodo, e le sottoclassi devono richiamarlo con `Task::init(period)` (slide 19–20), altrimenti `myPeriod` e `timeElapsed` restano non inizializzati.
>> `updateAndCheckTime` è chiamato dallo scheduler a ogni periodo base: accumula il tempo trascorso e restituisce `true` quando si raggiunge il periodo del task. Conseguenze: il primo `tick` avviene dopo un intero periodo (non a t = 0); e poiché `timeElapsed` viene azzerato invece di fare `timeElapsed -= myPeriod`, se il periodo non è multiplo del periodo base il task gira più lentamente del previsto (es. periodo 120 con base 50 → eseguito ogni 150 ms). Con il periodo base = MCD dei periodi questo non succede.

## Slide 21 – REMARKS

- Implicit strong discipline to be adopted in task design
	- the execution of the tick method should have a duration always less than the scheduler period
- A different way to use timers and interrupts in schedulers concerns implementing the schedule step (schedule, tick) directly inside the interrupt/timer handler
	- **interrupt-driven schedulers**
	- main drawback
		- task execution would be inside interrupt handlers => constraints and limitations

>> Nello scheduler cooperativo visto finora l'interrupt del timer si limita ad alzare un flag e i `tick()` girano nel `loop()`: se un ciclo sfora il periodo, semplicemente un tick del timer va perso o arriva in ritardo.
>> Nella variante *interrupt-driven* i `tick()` girano dentro l'ISR: durante l'esecuzione gli altri interrupt sono di norma disabilitati, quindi niente `delay()`, niente `Serial` affidabile, `millis()` che non avanza, e i task devono essere brevissimi. In cambio la periodicità è più precisa.

## Slide 22 – TASK DEPENDENCIES

- Task can have dependencies that requires various form of interactions
	- *temporal dependencies*
		- e.g.: a task T3 can be executed only after tasks T1 and T2
	- *producers/consumers*
		- e.g. a task T1 needs an info produced by a task T2
	- *data-oriented*
		- e.g. task T1 and T2 need to share some data
- In our case we represent and manage these dependencies through **shared variables**

## Slide 23 -> 24 – EXAMPLE: MOTION-TRIGGERED LAMP SYSTEM

- Let's consider an embedded system in which a led is switched on as soon as some movement is detected, in some environment
	- it is equipped with a movement sensor, connected on the input pin P4
	- a movement is detected when it happens that P4 is sampled to be HIGH for two times in sequence, considering a period of 200ms.
	- when a movement is detected, a led connected to the output pin P4 should be switched on and keep the light on for 10 seconds, after the last detection time
	- the system includes a led, connected to P2, that should blink with period 200ms when a movement is detected (and keeps being detected)
- Design with three tasks
	- DetectMotion
	- IlluminateLamp
	- BlinkLed

>> Refuso: il terzo sotto-punto parla di "a led connected to the output pin P4", ma P4 è il pin d'**ingresso** del sensore. Dal diagramma della slide 24 si tratta della **lampada** (LAMP) sul pin d'uscita **P3**. Anche nel primo punto "a led is switched on" indica in realtà la lampada.

![[IOT23-s024-1.png|700]]

- P2 - out pin => LED
- P3 - out pin => LAMP
- P4 - in pin => SENSOR

>> **DetectMotion** (periodo 200 ms, ingresso P4, scrive la variabile condivisa `boolean mnt`). Stato iniziale DM0.
>>
>> | Stato (azione) | Condizione | Stato successivo |
>> |---|---|---|
>> | DM0 (`mnt=false`) | `!P4` | DM0 |
>> | DM0 | `P4` | DM1 |
>> | DM1 | `!P4` | DM0 |
>> | DM1 | `P4` | DM2 |
>> | DM2 (`mnt=true`) | `P4` | DM2 |
>> | DM2 | `!P4` | DM0 |
>>
>> **IlluminateLamp** (periodo 200 ms, legge `mnt`, variabile locale `unsigned char cnt`, uscita P3). Stato iniziale IL0.
>>
>> | Stato (azione) | Condizione / azione sulla transizione | Stato successivo |
>> |---|---|---|
>> | IL0 (`P3=0`) | `!mnt` | IL0 |
>> | IL0 | `mnt` | DM1 |
>> | DM1 (`P3=1`) | `mnt` | DM1 |
>> | DM1 | `!mnt` / `cnt = 0` | DM2 |
>> | DM2 (`cnt++`) | `!mnt && cnt < 50` | DM2 |
>> | DM2 | `mnt` | DM1 |
>> | DM2 | `!mnt && cnt >= 50` | IL0 |
>>

## Slide 25 – SHARED VARIABLES, ATOMIC ACTIONS AND RACE CONDITIONS

- Generally speaking, shared variables among concurrent tasks may lead to race conditions, in the case of concurrent reads/writes
- In our case (cooperative) there could not be races
	- each task tick is executed by the scheduler in sequence
	- the execution is atomic from the point of view of the whole system
- However the execution of multiple ticks of a task can be interleaved with the ones of other tasks
	- this may lead to high-level races, in some cases

>> Un singolo `tick()` non viene mai interrotto da un altro task, quindi nessuno vede una variabile "scritta a metà". Un'operazione logica che però richiede **più tick** dello stesso task (es. leggere un valore in un tick e aggiornarlo in quello successivo, basandosi su quanto letto) può essere intervallata dai tick di altri task che nel frattempo modificano la variabile: è una race "di alto livello", a livello di logica applicativa.
>> Attenzione: gli interrupt restano asincroni. Una variabile condivisa fra una ISR e il loop (es. il flag del timer) va dichiarata `volatile` e, se è più grande di un byte, letta con gli interrupt disabilitati.

## Slide 26 – EXPLOITING THE SLEEP MODE

- If the period of a scheduler is large enough, we can exploit the timer-driven behaviour and the sleep modality to save power
	- at each cycle, the scheduler after executing the task ticks, it goes to sleep until the next timer tick awakes it for the next cycle
- This is a very important extension for systems that are battery powered
	- nevertheless, in order to be applied, the scheduler period should be large enough to make irrelevant the latency of the microcontroller / MCU board to enter/exit the sleep modality

>> Risolve il problema di efficienza del *busy waiting*: invece di girare a vuoto aspettando il flag del timer, la CPU dorme e l'interrupt del timer la risveglia. Il timer usato per il risveglio deve restare attivo nella modalità di sleep scelta.

## Slide 27 – CPU USAGE AND SCHEDULING

- In synchronous FSM, we assume that actions have zero duration (i.e. instantaneous)
	- or: we abstract from their real duration
- Actually in the real system actions have always a duration and we need to carefully check that the chosen period is compatible with that duration, to avoid problems

## Slide 28 – OVERRUN EXCEPTION
*(slide marcata "IMPORTANT")*

- **Overrun exception -** when the execution time of actions exceeds the period
	- it is called a *timer overrun* if the scheduler is timer-based using interrupts (interrupt-driven schedulers)
		- in that case a new interrupt is generated before the conclusion of the interrupt handler
- Overrun example

![[IOT23-s028-1.png|500]]

sync machine with period = 100ms

Depending on the state, different actions are executed. At t = 200ms, the duration of actions exceed the period…

>> Lettura del diagramma: ogni rettangolo è l'esecuzione delle azioni in un tick. A 0 e a 100 ms le azioni finiscono ben prima del tick successivo. A 200 ms le azioni durano più di 100 ms e sono ancora in corso a 300 ms: il tick dei 300 ms (rettangolo tratteggiato e barrato) non può essere eseguito in tempo e va perso o slitta. Si riparte regolarmente al tick dei 400 ms.
>> Conseguenza: la FSM salta un campionamento e il comportamento temporale non è più quello progettato (es. contatori di tick che misurano tempi sbagliati).

## Slide 30 – CPU UTILISATION PARAMETER AND WORST-CASE EXECUTION TIME

- The **CPU utilisation parameter** is the percentage of time in which the CPU (microcontroller) is used to execute a task:

**U = (time used for a task by the CPU / total time) * 100%**

- The **Worst-Case-Execution-Time** (**WCET**) is the execution time in a period in the worst case
	- In the case of multiple states/transitions, we consider the longest sequence of instructions

>> Per un task periodico si calcola su un periodo, usando il caso peggiore: $U = \dfrac{WCET}{T} \cdot 100\%$, dove $T$ è il periodo.
>> Con più stati il WCET è il ramo più costoso: le azioni della transizione più lunga più quelle dello stato più costoso, non la media.

---
## Slide 31 – OVERRUN CASE

- We compute U. If U is > 100%, then an overrun exception may occur
- In that case, in order to solve/avoid the problem, we can:
	- increase the period of the FSM
	- optimise the sequence of instructions to reduce the WCET
	- break long sequences in smaller sequences of actions
	- use a faster MCU
	- remove functionalities/behaviours from the system

>> "Break long sequences" significa spezzare un'azione lunga su più stati/tick, in modo che ogni tick resti sotto il periodo (es. elaborare un buffer un pezzo per volta).
>> Aumentare il periodo funziona solo se i requisiti temporali lo permettono: nell'esempio della slide 23 il periodo di 200 ms è imposto dal campionamento del sensore e dal lampeggio.

---
## Slide 32 – CPU UTILISATION & WCET IN THE CASE OF MULTIPLE TASKS

- The analysis of CPU utilisation factor is even more frequent in systems with multiple tasks
- If tasks have the same period, then the WCET is computed by summing the individual WCETs of the tasks

>> Con periodo comune $T$: $WCET = \sum_i WCET_i$ e $U = \dfrac{\sum_i WCET_i}{T} \cdot 100\%$, che deve restare sotto il 100%. Es. i tre task della slide 24 hanno tutti periodo 200 ms, quindi la somma dei loro WCET deve stare sotto i 200 ms (in pratica anche considerando il tempo dello scheduler stesso).

## Slide 35 – WHEN PERIODS ARE DIFFERENT

- In the general case, tasks can have *different periods*
- The WCET can be calculated by considering the **hyper-periods:**
	- periods that are the minimum common multiplier of the periods
- Example: LedShow - BL with period 300ms and TL period 200ms
	- in questo caso, il pattern si ripete ogni 600 ms
	- in 600 ms, BL executes 600/300 = 2 times, while TL executes 600/200 = 3 times
	- the U parameter in the hyper-period is: (2*20ms+3*90ms)/600ms = 55%

![[IOT23-s035-1.png|650]]

>> Nella slide la riga "in questo caso, il pattern si ripete ogni 600 ms" (scritta in italiano) è quasi del tutto coperta dal diagramma. È ricostruita dal testo del PDF.
>> "Minimum common multiplier" sta per *least common multiple* (minimo comune multiplo). Iper-periodo: $H = \text{mcm}(300, 200) = 600$ ms. Inoltre sull'iper-periodo si calcola $U$, non il WCET: il WCET resta quello del singolo task.
>> **Errore di calcolo nella slide**: con i numeri scritti, $\frac{2 \cdot 20 + 3 \cdot 90}{600} = \frac{40 + 270}{600} = \frac{310}{600} \approx 51{,}7\%$, non 55%.
>> Il 55% torna invece con il WCET di BL = 30 ms, come nelle slide 33 e 39: $\frac{2 \cdot 30 + 3 \cdot 90}{600} = \frac{60 + 270}{600} = \frac{330}{600} = 55\%$. Quindi il "20ms" è un refuso per 30 ms. Anche il diagramma lo conferma: i rettangoli di BL sono larghi circa 30–35 ms, contro circa 90 ms per TL. Con 20 ms sarebbero lunghi meno di un quarto di quelli di TL.
>> In modo equivalente: $U = \sum_i \frac{WCET_i}{T_i} = \frac{30}{300} + \frac{90}{200} = 0{,}10 + 0{,}45 = 55\%$.
>> Lettura del diagramma: a 0 (e a 600) sono pronti entrambi. BL va da 0 a 30 ms e TL, che aspetta (tratteggio), da 30 a 120 ms. Poi TL gira da sola a 200 e a 400, BL da sola a 300.
>> Nota: lo scheduler cooperativo della slide 15 ha periodo base pari al MCD dei periodi, cioè 100 ms. A $t = 0$, però, BL + TL = 30 + 90 = 120 ms > 100 ms: il tick dei 100 ms viene superato anche se $U = 55\%$. È proprio il caso "multiple tasks: overrun can still occur" della slide 36.

## Slide 36 – SUMMING UP

- Steps for the U calculation for T₁...Tₙ tasks over a microcontroller M
	- we determine the duration R of a single instruction of the MCU
	- we analyse the code of each Tᵢ, computing its WCET
		- we first compute the max number of instructions in a tick and the we multiply it for R
	- we determine the hyper-period H, as minimum common multiplier among the periods of all tasks (T1.H, T2.H,…)
	- U is then computed as:

$$\mathbf{U} = \frac{\frac{H}{T1.period} \cdot T1.WCET + \frac{H}{T2.period} \cdot T2.WCET + \dots}{H} \cdot 100$$

- U > 100 => there will be overrun
- U < 100 =>
	- for a single task: overrun cannot occur
	- multiple tasks: overrun can still occur

>> Sulla slide la formula è scritta in linea come "(…)/ H*100", ma va letta come (…) diviso H, il tutto per 100. "(T1.H, T2.H,…)" va inteso come i periodi dei task (T1.period, T2.period, …); "the we multiply" è un refuso per "then we multiply".
>> Siccome $H / T_i$ è il numero di esecuzioni di $T_i$ nell'iper-periodo, la formula si semplifica in $U = \sum_i \frac{WCET_i}{T_i.period} \cdot 100$: l'iper-periodo serve a "vedere" lo schema che si ripete, ma il risultato non dipende da H.
>> Con i dati delle slide 35/39: $H = 600$, $U = \frac{(600/300) \cdot 30 + (600/200) \cdot 90}{600} \cdot 100 = \frac{330}{600} \cdot 100 = 55$.
>> Caso limite: con un solo task, $U = 100$ vuol dire WCET = periodo; non c'è overrun, ma non resta alcun margine.
>> Perché con più task può esserci overrun anche con $U < 100$: $U$ è una media sull'iper-periodo. Se in un tick sono pronti insieme più task, la somma dei loro WCET può superare il periodo base dello scheduler, come succede a $t = 0$ nell'esempio della slide 35 (120 ms > 100 ms). $U \le 100$ è quindi una condizione necessaria ma non sufficiente.

## Slide 37 – JITTER

- The **jitter** is the delay that occurs between the time in which a task is ready to be executed and the time in which the task is effectively executed
- Different scheduling strategies may lead to different jitters
	- LedShow example
		- if BL has priority => the jitter of BL is 0, while the jitter of TL is 30ms
		- if TL has priority => the jitter of BL is 90ms, while the jitter of TL is 0
- In general, giving priority to shortest tasks leads to minimise the average jitter
	- in the example: priority to BL

>> Verifica: i valori sono coerenti con WCET(BL) = 30 ms e WCET(TL) = 90 ms (slide 33 e 39). Chi non ha priorità aspetta l'intero WCET dell'altro: TL aspetta 30 ms, BL aspetta 90 ms. Con il WCET di BL = 20 ms scritto nella slide 35, il jitter di TL sarebbe 20 ms: è un'altra conferma che quel 20 è un refuso.
>> Coerenza con i diagrammi della slide 39 (periodi 300/200 ms): 30 ms e 90 ms sono i jitter **massimi**, che si hanno solo quando i due task sono pronti insieme (a 0 e a 600 ms). Negli altri istanti (TL a 200 e a 400, BL a 300) il jitter è 0, perché l'altro task non è in esecuzione.
>> Jitter medio sull'iper-periodo di 600 ms (5 esecuzioni: 2 di BL e 3 di TL):
>> - priorità a BL: $(0 + 0 + 30 + 0 + 0)/5 = 6$ ms;
>> - priorità a TL: $(90 + 0 + 0 + 0 + 0)/5 = 18$ ms.
>>
>> Conviene quindi dare priorità a BL, il task più corto (la stessa idea dello *Shortest Job First*). Con lo stesso periodo di 500 ms (slide 33) la media per esecuzione è 15 ms contro 45 ms.
>> Nello scheduler della slide 16 la "priorità" è semplicemente l'ordine in cui i task sono stati aggiunti con `addTask`: `schedule()` scorre `taskList` dal primo all'ultimo.

## Slide 38 – DEADLINE

- The **deadline** is defined as the interval of time within which a task *must* be executed after being ready to execute (in each period)
- If a task is not executed within its deadline, we have a ***missed-deadline exception*** that can result in a system failure
	- if a deadline is not specified, then it is its period, by default
- The scheduling strategy impacts on jitters and then also on the possibility to have missed-deadline exceptions

>> La deadline è relativa all'istante in cui il task diventa pronto: con deadline $D$, il task pronto all'istante $t$ deve **terminare** entro $t + D$. Con uno scheduler cooperativo (senza preemption) la deadline è rispettata se $\text{jitter} + WCET \le D$. Per questo la strategia di scheduling, che determina il jitter, influisce sulle deadline mancate.

	- TL has period = 200ms, WCET 90ms and deadline 100ms

- If we give priority to TL:

## Slide 40 – STATIC AND DYNAMIC PRIORITY SCHEDULING

- The **priority** concerns the order in which the tasks are executed
	- where there are multiple tasks that are ready, then the scheduler selects always the one with the higher priority
	- we can have both static and dynamic approaches in assigning the priority to tasks
		- static => priority assigned at design time and do not change at runtime
		- dynamic => priority assigned dynamically, according different strategies
- Key aspect in real-time OS (RTOS)
	- next modules

>> Esempi: lo scheduler della slide 16 ha priorità statica, cioè l'ordine di `addTask`. Ci sono anche criteri statici classici, come *Rate Monotonic* (priorità al periodo più breve) e *Deadline Monotonic* (priorità alla deadline relativa più breve, come nella slide 39). Un esempio di priorità dinamica è *Earliest Deadline First* (EDF): a ogni scelta esegue il task pronto con la deadline assoluta più vicina.

## Slide 41 – PERIODIC AND SPORADIC TASKS

- The tasks considered so far are **periodic**
	- they are executed periodically by the scheduler, given a period p, and this period corresponds to the period of the synchronous FSM
	- typically periodic tasks are static, that is: launched when the system is started and never removed
- Besides periodic tasks we can have **sporadic or aperiodic tasks**
	- i.e. tasks that are executed at arbitrary times

>> La slide usa "sporadic" e "aperiodic" come sinonimi. Nella teoria del real-time, però, un task *sporadico* ha un tempo minimo garantito fra due attivazioni (e quindi si può analizzare quasi come un periodico), mentre un task *aperiodico* non ha alcun vincolo. Esempi: la gestione della pressione di un pulsante, o l'invio di un messaggio quando arriva un comando.

## Slide 42 – MANAGING APERIODIC TASKS

- Basic capabilities of a scheduler managing aperiodic tasks
	- *dynamic* insertion and removal of tasks
	- dynamic assignments of priorities
- Simple examples (in lab)
	- aperiodic task simulation with periodic tasks with "idle" state
		- simplest approach, not super efficient
	- tasks with active/not active meta-state
		- selected by a scheduler only if active
		- can be activated/de-activated by other tasks too

>> Approccio "idle": il task resta periodico ma, finché non c'è nulla da fare, rimane in uno stato IDLE della sua FSM. Il suo `tick()` viene comunque chiamato a ogni periodo, e questo consuma CPU (da qui "not super efficient"); inoltre la reazione può arrivare fino a un periodo dopo l'evento.
>> Meta-stato attivo/non attivo: è una condizione esterna alla FSM del task. Lo scheduler controlla, per esempio con un metodo `isActive()`, se il task è attivo prima di chiamare `updateAndCheckTime`/`tick`, e salta quelli non attivi. Un altro task può attivarlo quando si verifica l'evento.

## Riassunto

>> **Architetture a task**
>> - Il software embedded si scompone in un insieme di **task concorrenti**: ognuno ha un compito ben delimitato ed è descritto da una FSM sincrona. Il comportamento globale nasce dalla loro esecuzione e interazione.
>> - Vantaggi: modularità (l'"interfaccia" di un task sono le variabili e gli oggetti che legge e scrive), task più semplici del tutto, debug più facile, riuso. Sfide: i task sono concorrenti e possono avere **dipendenze** (temporali, produttore/consumatore, dati condivisi), gestite qui con **variabili condivise**.
>> - Implementazione: classe astratta `Task` con `init()` (chiamato una volta) e `tick()` (lo "step" della FSM, chiamato a ogni periodo). Ogni task concreto la estende.
>>
>> **Scheduler cooperativo**
>> - Con periodi diversi serve uno **scheduler**: tiene la lista dei task e ha un periodo base pari al **MCD** dei periodi dei task. A ogni tick base chiama `updateAndCheckTime(basePeriod)` su ogni task, e chiama `tick()` solo su quelli il cui periodo è scaduto (round-robin).
>> - Disciplina: **ogni `tick()` deve durare meno del periodo dello scheduler**. In alternativa si usano scheduler guidati da interrupt, con i vincoli degli interrupt handler.
>> - Nel cooperativo non ci sono race "a basso livello", perché ogni tick è atomico rispetto al sistema. Possono però esserci race di alto livello fra sequenze di tick di task diversi.
>> - Se il periodo è abbastanza lungo, tra un tick e l'altro l'MCU può andare in **sleep** per risparmiare energia (importante con le batterie).
>>
>> **Analisi dell'esecuzione**
>> - Le azioni non hanno durata nulla. Se il tempo di esecuzione supera il periodo si ha un'**overrun exception** (*timer overrun* negli scheduler a interrupt). Si individua analizzando il codice: si stimano le istruzioni nel caso peggiore.
>> - **WCET**: tempo di esecuzione nel caso peggiore (la sequenza di istruzioni più lunga). **U** = tempo di CPU usato / tempo totale × 100.
>> - Con periodi uguali i WCET si sommano. Con periodi diversi si ragiona sull'**iper-periodo** H = mcm dei periodi: $U = \frac{\sum_i (H/T_i) \cdot WCET_i}{H} \cdot 100 = \sum_i \frac{WCET_i}{T_i} \cdot 100$.
>> - U > 100% → ci sarà overrun. U < 100% → con un solo task niente overrun, ma con più task può ancora capitare (es. slide 35: a t=0 BL+TL = 120 ms > 100 ms di periodo base).
>> - Rimedi: periodo più lungo, codice ottimizzato, azioni spezzate in sequenze più corte, MCU più veloce, meno funzionalità.
>> - Esempi LED-show: 24% (slide 33), 110% → overrun (slide 34), 55% con periodi 300/200 ms (slide 35: il calcolo torna con WCET di BL = 30 ms, non 20).
>> - **Jitter**: ritardo fra quando un task è pronto e quando viene eseguito. **Deadline**: entro quando deve essere eseguito (di default il suo periodo); se la manca si ha una *missed-deadline exception*.
>> - La strategia di scheduling cambia jitter e deadline. Dare priorità al task più corto minimizza il jitter medio (BL), ma nell'esempio della slide 39 fa mancare la deadline di TL (100 ms). Con priorità a TL il jitter cresce ma le deadline sono rispettate.
>>
>> **Priorità e task aperiodici**
>> - Priorità **statica** (decisa a progetto) o **dinamica** (decisa a runtime): tema centrale degli RTOS, trattato nei prossimi moduli.
>> - Oltre ai task periodici esistono task **sporadici/aperiodici**, eseguiti in momenti arbitrari. Lo scheduler deve poterli inserire e togliere e cambiarne la priorità. Nei lab si simulano con task periodici con stato "idle" oppure con task attivi/non attivi.
