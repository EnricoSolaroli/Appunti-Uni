## Slide 3 – DESIGN AND DEVELOPMENT OF EMBEDDED SOFTWARE

- Two main modelling approaches
	- **top-down approach**
		- starting from the *domain* and its modelling using high-level paradigms, such as OO
	- **bottom-up approach**
		- starting from the hardware characteristics and related concepts
- This module is about a *top-down approach*

>> In pratica: nel **top-down** si parte dai concetti del problema (pulsante, luce, controllore...) e solo alla fine li si mappa su pin, registri e periferiche; nel **bottom-up** si parte da ciò che offre l'hardware (pin digitali, ADC, timer, interrupt) e si costruisce il software sopra.

## Slide 4 – MODELLING AND PROGRAMMING

- Programming paradigms such as OO are first of all ***modelling paradigms***
	- they specify how we can conceptualise, represent, model a system
	- howe we can analyse a problem and define the corresponding solution in some application domain
- **Model**
	- representation of relevant aspects of a system, abstracting from those that are considered not relevant
	- relevant aspects concern the structure, behaviour and interaction of the system
- Strong relationships between modelling and programming [OLE]
	- scandinavian school, where part of the OO is rooted

Ole Lehrmann Madsen, Birger Møller-Pedersen. *A Unified Approach to Modeling and Programming*, Model Driven Engineering Languages and Systems. Lecture Notes in Computer Science Volume 6394, 2010, pp 1-15.

>> "Scuola scandinava": il paradigma OO nasce in Norvegia con il linguaggio **Simula** (Dahl e Nygaard, anni '60), pensato proprio per *modellare e simulare* sistemi reali; da qui l'idea che programmare sia prima di tutto modellare.

## Slide 8 – OBJECT-ORIENTED PARADIGM

- Main paradigm in modelling and programming software
	- effective level of abstraction to capture and represent essential aspects of the problem and its domain
- Fostering important properties at the design and programming level
	- **modularity**
	- **encapsulation**
	- **reuse** and **extensibility** mechanism
- Among important aspects not directly captured by the paradigm
	- concurrency, asynchronous interactions, distribution

>> I limiti citati nell'ultimo punto sono proprio quelli rilevanti nei sistemi embedded (eventi asincroni dai sensori, interrupt, più attività "contemporanee"): per questo nei moduli successivi il modello OO verrà affiancato da architetture di controllo specifiche (super-loop, event-loop, macchine a stati, task).

## Slide 9 – MODELLING EMBEDDED SOFTWARE BASED ON MICRO-CONTROLLERS

- Two main macro parts
	- **controller**
		- encapsulating the control/application logic concerning the task(s) to do
		- to this purpose, it accesses/uses/observes passive resources and devices
		- active component, based on some *control architecture*
	- **controlled elements**
		- modelling the resources and devices managed/used by the controller to do its job
			- e.g. I/O devices, sensors, actuators
		- encapsulates functionalities useful for the controller
		- passive component

>> **Attivo vs passivo**: il controller ha un proprio flusso di controllo (decide *quando* fare qualcosa, es. ciclando nel `loop()`); gli elementi controllati non fanno nulla di propria iniziativa, ma offrono operazioni che il controller invoca (es. `isPressed()`, `switchOn()`).

---
## Slide 10 – FEATURES

- **Controller**
	- Integrating pro-active and re-active behaviour
	- based on a *control loop* architecture
		- simplest one: super-loop
		- in a future module: event-loop
- **Controlled elements**
	- well-defined interface
	- observable state and events
	- reusability, controllability
	- OO model

>> **Pro-attivo** = il controller agisce per iniziativa propria, inseguendo i suoi obiettivi (es. far lampeggiare un led ogni secondo); **re-attivo** = risponde a eventi/cambiamenti dell'ambiente (es. il pulsante viene premuto).
>> **Super-loop**: un unico ciclo infinito che a ogni iterazione legge gli input, elabora e aggiorna gli output; in Arduino è la funzione `loop()`, richiamata di continuo dopo `setup()`.

## Slide 13 – CONTROLLER: CONTROL LOOP

- **Control** loop — based on a super-loop architecture in this case

```
lightOn := false

loop {
  /* first: sensing */
  bool isPressed = button.isPressed();

  /* processing and acting */
  if (!lightOn && isPressed){
    light.switchOn()
    lightOn := true
  } else if (lightOn && !isPressed){
    light.switchOff()
    lightOn := false
  }
}
```

>> Struttura tipica di ogni iterazione del super-loop: **sensing** (lettura degli input) → **processing** (decisione) → **acting** (comando degli output).
>> La variabile `lightOn` memorizza lo stato della luce: così `switchOn()`/`switchOff()` vengono chiamati solo **al cambiamento** (pulsante appena premuto / appena rilasciato) e non a ogni iterazione del ciclo.
>> Nel pseudocodice l'oggetto è chiamato `light` anche se nel modello della slide 12 l'interfaccia si chiama `Led`: nelle slide successive l'interfaccia viene infatti rinominata `Light` e `Led` diventa la sua implementazione concreta.

## Slide 14 -> 18 – FROM MODELS TO CODE: ARDUINO IN WIRING/C++

![[IOT21-s014-1.png|250]]

`Light.h`

```cpp
#ifndef __LIGHT__
#define __LIGHT__

class Light {
public:
  virtual void switchOn() = 0;
  virtual void switchOff() = 0;
};

#endif
```

`Led.h`

```cpp
#ifndef __LED__
#define __LED__

#include "Light.h"

class Led: public Light {
public:
  Led(int pin);
  void switchOn();
  void switchOff();
protected:
  int pin;
};

#endif
```

```cpp
/* Led.cpp */
#include "Led.h"
#include "Arduino.h"

Led::Led(int pin){
  this->pin = pin;
  pinMode(pin,OUTPUT);
}

void Led::switchOn(){
  digitalWrite(pin,HIGH);
}

void Led::switchOff(){
  digitalWrite(pin,LOW);
};
```

>> Nel diagramma UML l'interfaccia `Light` ha i metodi in *corsivo* (= astratti) e la freccia con triangolo vuoto indica che `Led` la **implementa/estende**.
>> `virtual ... = 0` dichiara un metodo **virtuale puro**: `Light` diventa una classe astratta (non istanziabile), l'equivalente C++ di un'interfaccia Java.
>> `#ifndef / #define / #endif` è l'**include guard**: evita che lo stesso header venga incluso (e quindi la classe definita) due volte nella stessa unità di compilazione.
>> Il `;` dopo l'ultima `}` di `Led::switchOff()` in `Led.cpp` è superfluo ma innocuo (dichiarazione vuota, ammessa da C++11). Il codice delle slide 14–18 compila senza errori.

- Light interface (in Light.h)
	- interface for any lighting device — in C++: an abstract class
- Led device
	- concrete type of Light
	- declaration of the Led class in Led.h
	- definition/implementation of the Led class in Led.cpp
- Remarks
	- C++ allows for separating class declaration from class definition
	- to use/access Arduino base library/procedures/constants in *.cpp files, the header "Arduino.h" must be included
		- not needed in the *.ino main file

>> Il file `.ino` non ha bisogno di `#include "Arduino.h"` perché l'IDE di Arduino, prima di compilare, lo trasforma in un `.cpp` aggiungendo automaticamente quell'include (e i prototipi delle funzioni). I file `.cpp`/`.h` della libreria, invece, sono compilati così come sono.

![[IOT21-s016-1.png|250]]

`Button.h`

```cpp
#ifndef __BUTTON__
#define __BUTTON__

class Button {

public:
  virtual bool isPressed() = 0;
};

#endif
```

`ButtonImpl.h`

```cpp
#ifndef __BUTTONIMPL__
#define __BUTTONIMPL__

#include "Button.h"

class ButtonImpl: public Button {
public:
  ButtonImpl(int pin);
  bool isPressed();

protected:
  int pin;
};
#endif
```

`ButtonImpl.cpp`

```cpp
#include "ButtonImpl.h"
#include "Arduino.h"

ButtonImpl::ButtonImpl(int pin){
  this->pin = pin;
  pinMode(pin, INPUT);
}

bool ButtonImpl::isPressed(){
  return digitalRead(pin) == HIGH;
}
```

>> `isPressed()` restituisce `true` quando il pin legge `HIGH`: presuppone un pulsante collegato con resistenza di **pull-down** (pin a `LOW` a riposo, `HIGH` quando premuto). Con `INPUT_PULLUP` la logica sarebbe invertita (premuto = `LOW`).

- `Button`
	- basic button interface
- `ButtonImpl`
	- a class implementing buttons

- Setup
	- objects creation
- Main (super-)loop

```cpp
#include "Led.h"
#include "ButtonImpl.h"

#define LED_PIN    13
#define BUTTON_PIN 2

Light* light;
Button* button;
boolean lightOn;

void setup(){
  light = new Led(LED_PIN);
  button = new ButtonImpl(BUTTON_PIN);
  lightOn = false;
}

void loop(){
  bool isPressed = button->isPressed();
  if (!lightOn && isPressed){
    light->switchOn();
    lightOn = true;
  } else if (lightOn && !isPressed){
    light->switchOff();
    lightOn = false;
 }
}
```

>> È la traduzione diretta del pseudocodice della slide 13: l'inizializzazione (`lightOn := false` e creazione degli oggetti) va in `setup()`, il corpo del ciclo in `loop()`.
>> Le variabili globali sono di tipo **puntatore all'interfaccia** (`Light*`, `Button*`), mentre gli oggetti creati con `new` sono delle classi concrete: grazie ai metodi `virtual`, `light->switchOn()` esegue `Led::switchOn()` (**polimorfismo**/binding dinamico). Per usare un altro dispositivo basta cambiare la riga in `setup()`.
>> `boolean` è un alias di `bool` definito da Arduino. Il pin 13 su Arduino UNO è collegato anche al led integrato sulla scheda.

## Slide 19 – REMARKS

- Object-Oriented level of abstraction
	- low-level implementation details (e.g. the specific wiring primitives used to drive pins) are hidden, not exposed to the controller

## Slide 20 -> 21 – EXTENSION: AN EXAMPLE

- Modelling a led with light intensity

![[IOT21-s020-1.png|450]]

>> Il diagramma descrive un "diamante": `LedExt` **estende** `Led` (ne riusa l'implementazione: `pin`, costruttore) e **realizza** l'interfaccia `LightExt`, che a sua volta estende `Light` aggiungendo `setIntensity(int)`. Così un `LedExt` può essere usato sia dove serve una `Light` sia dove serve una `LightExt`.
>> La freccia tratteggiata fra `LightExt` e `Light` in UML indicherebbe una realizzazione; nel codice (slide 21) è un'ereditarietà normale (`class LightExt : public Light`), cioè un'interfaccia che estende un'altra interfaccia.

- Modelling a led with light intensity

`LightExt.h`

```cpp
#ifndef __LIGHT_EXT__
#define __LIGHT_EXT__
#include "Light.h"

class LightExt : public Light {
public:
   virtual void setIntensity(int) = 0;
};
#endif
```

`LedExt.h`

```cpp
#ifndef __LED_EXT__
#define __LED_EXT__
#include "Led.h"
#include "LightExt.h"

class LedExt:  public LightExt, public Led {
public:
  LedExt(int pin);
  LedExt(int pin, int intensity);
  void switchOn();
  void switchOff();
  void setIntensity(int v);
private:
  int currentIntensity;
  bool isOn;
};
#endif
```

`LedExt.cpp`

```cpp
#include "LedExt.h"
#include "Arduino.h"

LedExt::LedExt(int pin) : Led(pin) {
  currentIntensity = 128;
  isOn = false;
}
LedExt::LedExt(int pin, int intensity) : Led(pin) {
  isOn = false;
  currentIntensity = intensity;
}

void LedExt::switchOn(){
  analogWrite(pin,currentIntensity);
  isOn = true;
}
void LedExt::setIntensity(int value){
 currentIntensity = value;
 if (isOn){
   analogWrite(pin,currentIntensity);
 }
}
void LedExt::switchOff(){
  analogWrite(pin,0);
  isOn = false;
}
```

>> - `analogWrite(pin, v)` genera un segnale **PWM** con duty cycle v/255 (v da 0 a 255): così si "simula" un'intensità intermedia. 128 ≈ 50% è l'intensità di default.
>> - Il costruttore `Led(pin)` della classe base imposta già `pinMode(pin, OUTPUT)`; `pin` è accessibile in `LedExt` perché in `Led.h` è dichiarato `protected`.
>> - `isOn` serve perché `setIntensity` non deve accendere il LED se è spento: memorizza solo il nuovo valore, che verrà usato al prossimo `switchOn()`.
>> - **Tranello C++ (diamond problem)**: `Led` e `LightExt` ereditano entrambe da `Light` in modo non virtuale, quindi un `LedExt` contiene **due** sotto-oggetti `Light`. Il codice compila (verificato con g++) e `LedExt::switchOn/switchOff` fanno override in entrambi i rami, ma la conversione `LedExt*` → `Light*` è **ambigua** (vedi slide 23). La soluzione standard è l'ereditarietà virtuale: `class Led : public virtual Light` e `class LightExt : public virtual Light`.

## Slide 22 – FADING

```cpp
#include "LedExt.h"

// the pin must by a PWM one
#define LED_PIN 9

LightExt* led;
int brightness;
int fadeAmount;

void setup(){
  brightness = 0;
  fadeAmount = 5;
  led = new LedExt(LED_PIN,brightness);
  led->switchOn();
}

void loop(){
  led->setIntensity(brightness);
  brightness = brightness + fadeAmount;

  if (brightness == 0 || brightness == 255) {
    fadeAmount = -fadeAmount ;
  }

  delay(20);
}
```

>> Cosa fa: la luminosità sale da 0 a 255 a passi di 5 e poi riscende, all'infinito. Ogni rampa sono 51 passi × 20 ms ≈ 1 s, quindi un ciclo completo (fade in + fade out) dura circa 2 s.
>> Il controller usa solo l'interfaccia `LightExt` (`LightExt* led`), non la classe concreta. Sull'Arduino UNO i pin PWM sono 3, 5, 6, 9, 10, 11 (segnati con `~`), per questo il pin 9.
>> Il test con `==` funziona solo perché 255 è multiplo di 5: con un passo di 7, ad esempio, `brightness` non varrebbe mai esattamente 255 e continuerebbe a crescere. Più robusto: `if (brightness <= 0 || brightness >= 255)`.
>> Refuso nel commento: "must by" → "must be".

## Slide 25 – SMART LIGHT CONTROLLER

- Control loop

```
lightOn := false

loop {
  detected := presDetector.detected()
  intens := lightSensor.getIntensity()
  isLowIntens := intens < LIGHT_THRESHOLD
  if (!lightOn && detected && isLowIntens){
    light.switchOn()
    lightOn := true
  } else if (lightOn && (!isLowIntens || !detected)){
    light.switchOff()
    lightOn := false
  }
}
```

>> Stessa struttura del button-led: prima *sensing* (legge i due sensori), poi decisione e azione. Accende se (spenta ∧ presenza ∧ buio), spegne se (accesa ∧ (luce sufficiente ∨ nessuno presente)).
>> Problema pratico: se il sensore di luce "vede" la lampada stessa, appena la luce si accende l'intensità supera la soglia e la luce si rispegne, poi si riaccende… (oscillazione). Anche senza questo effetto, valori vicini a `LIGHT_THRESHOLD` causano sfarfallio: di solito si usa un'**isteresi** (due soglie diverse per accendere e spegnere).

## Slide 26 – CONTROL LOOP AND FINITE STATE MACHINES

- Execution model based on a control loop (or super loop)
	- at each cycle the controller read the input state and choose the proper action to perform
		- the choice of the action depends on the current *state*
		- the action can lead to update the current state
- Need of having proper formalisms to describe state-based behaviours
	- **Finite State Machines (FSM)**
		- synchronous, asynchronous
	- next module

>> Negli esempi visti la variabile `lightOn` è proprio lo stato: il controller è una FSM a due stati (OFF, ON), le condizioni sugli input sono le transizioni e `switchOn()`/`switchOff()` sono le azioni eseguite durante la transizione.

---
## Slide 27 – CONTROL LOOP: ABOUT EFFICIENCTY AND REACTIVITY

- **Efficiency**
	- in the examples the loop is always cycling even if the controller is conceptually waiting for an input
- **Reactivity**
	- depends on how fast a cycle is completed
	- if during a single cycle sensors change states multiple times, these changes are not detected

>> Efficienza: è il *busy waiting* (polling continuo); la CPU è sempre al 100% e consuma energia anche se non succede nulla, un problema serio per dispositivi a batteria. Alternative: modalità sleep e interrupt (moduli successivi).
>> Reattività: gli input vengono letti solo una volta per ciclo. Se un ciclo dura 100 ms, una pressione del pulsante di 30 ms che cade fra due letture va persa; più in generale non si possono cogliere eventi più brevi del periodo del loop.

## Slide 28 – ABOUT REACTIVITY: EXAMPLE

- *"Implement a controller for making a continuous fade in and fade out of a led, with duration DT seconds, using a button to start and stop asynchronously the process"*
- Simple solution …

```
running := false
loop {
  if (button.switchedOn() &&
      !running){
    running := true
    light.switchOn()
  } else if (button.switchedOff()
             && running){
    running := false
    light.switchOff()
  }
  if (running){
    fadeIn()
    fadeOut()
  }
}
```

```
fadeIn(){
  intensity := 0
  delta := 1/NUM_STEPS;
  for (i := 0; i < NUM_STEPS; i++){
    intensity := intensity + delta
    light.setIntensity(intensity)
    sleep(DeltaTime)
  }
}

fadeOut(){...}
```

**PROBLEM:**
**if the button changes during the fade in/out, the controller does not detect it…**

>> Qui l'intensità è normalizzata fra 0 e 1 (`delta = 1/NUM_STEPS`) e ogni fade dura `NUM_STEPS × DeltaTime`. Un singolo ciclo del loop dura quindi un intero fade in + fade out (≈ DT): per tutto quel tempo il pulsante non viene letto, quindi lo stop non è "asincrono" come richiesto e una pressione breve durante il fade viene persa del tutto.
>> Idea della soluzione (ripresa nei moduli successivi): non bloccare il loop dentro un `for` con `sleep`, ma eseguire **un solo passo** del fade per ogni iterazione, ricordando in variabili di stato a che punto si è (fase in/out, intensità corrente). Così il pulsante viene controllato a ogni passo: è esattamente una macchina a stati.

## Slide 29 – THE CONTROLLER AS AN ACTIVE ENTITY

- About the conceptual nature of the controller
	- can it be modelled conceptually as an object in OO modelling?
- Actually objects in OO modelling/design/programming are typically passive entities
	- featuring proper interfaces to be used by the client of the object
	- they don't encapsulate a control flow
- The controller conceptually is an active entity, with its own logical control flow
	- at the design level, it is meant to encapsulate the control strategy of the system
- *So what kind of abstraction can be used to model this kind of entities?*

>> Un oggetto (es. `Led`) fa qualcosa solo quando qualcuno ne invoca un metodo; il controller invece "vive" da solo: decide quando leggere i sensori e quando agire, senza che nessuno lo chiami. Nel codice Arduino questo flusso di controllo autonomo è il `loop()`.

## Slide 30 – CONTROLLER MODEL: AGENTS

- We will use the concept of "**agent**" to model controllers
	- agents are first-class active entities, equipped with an autonomous logical control flow, designed to achieve or perform some task(s) that call for being reactive to data and events perceived from the environment (through sensors), and that do actions to have an effect on the environment though some actuators
- Agent as first-class design abstraction
	- reactive + pro-active behaviour
	- encapsulating a control flow
	- *task-oriented* design

>> **Reattivo** = risponde a eventi/dati percepiti (es. il pulsante premuto); **pro-attivo** = agisce di propria iniziativa per portare avanti il suo compito (es. far proseguire il fade anche senza nuovi input). Oggetti passivi (sensori, attuatori) + agenti attivi (controller) sono le due astrazioni di base del modello.

## Slide 32 – CONTROL LOOP - TASK-BASED DECOMPOSITION AND EXECUTION

## Riassunto

>> **Modellare prima di programmare**
>> - Approccio **top-down**: si parte dal dominio e lo si modella con paradigmi di alto livello (OO). L'approccio bottom-up parte invece dall'hardware.
>> - Un **modello** rappresenta gli aspetti rilevanti di un sistema e astrae dal resto. Le tre dimensioni da modellare sono **struttura** (le parti), **comportamento** (cosa fa ogni parte) e **interazione** (come le parti comunicano).
>> - Vantaggi: si capisce meglio il sistema, il codice è più portabile, riusabile ed estendibile, e si può verificarne la correttezza in modo più rigoroso. UML è il linguaggio di modellazione di riferimento.
>> - Il paradigma OO non cattura direttamente concorrenza, interazioni asincrone e distribuzione.
>>
>> **Controller ed elementi controllati**
>> - Il **controller** incapsula la logica di controllo ed è il componente **attivo**: ha il control loop (super-loop; più avanti l'event loop) e unisce comportamento proattivo e reattivo.
>> - Gli **elementi controllati** (dispositivi di I/O, sensori, attuatori) sono **passivi**: hanno un'interfaccia ben definita, uno stato osservabile e degli eventi, e sono modellati come oggetti.
>> - Esempio pulsante-LED: interfaccia `Button` con `isPressed()`, interfaccia `Led`/`Light` con `switchOn()` e `switchOff()`. Il controller legge il pulsante (*sensing*), decide e agisce sul LED.
>>
>> **Dal modello al codice (C++/Arduino)**
>> - Interfaccia = classe astratta con metodi virtuali puri (`Light`, `Button`); classe concreta = implementazione legata ai pin (`Led`, `ButtonImpl`). Dichiarazione nel `.h`, definizione nel `.cpp`, che deve includere `Arduino.h`.
>> - Il controller usa solo le interfacce (`Light*`, `Button*`): i dettagli di cablaggio restano nascosti, a vantaggio di leggibilità, portabilità e riuso.
>> - Estensione: `LightExt` aggiunge `setIntensity()` e `LedExt` la implementa con PWM (`analogWrite`), da cui l'esempio di fading.
>> - Attenzione (segnalato nella nota): con l'ereditarietà della slide 21, `LedExt` contiene due sotto-oggetti `Light`. Senza ereditarietà virtuale non si può assegnare a un `Light*`.
>>
>> **Limiti del control loop**
>> - **Efficienza**: il loop gira sempre, anche quando non c'è nulla da fare.
>> - **Reattività**: dipende dalla durata di un ciclo. Se un input cambia più volte durante un ciclo, i cambiamenti si perdono. Esempio: durante un `fadeIn()` con `sleep` il pulsante non viene letto.
>> - I comportamenti basati sullo stato si descrivono con le **macchine a stati finiti** (sincrone e asincrone): sono l'argomento del prossimo modulo.
>>
>> **Il controller come agente**
>> - Gli oggetti sono passivi e non incapsulano un flusso di controllo. Il controller invece è un'entità attiva, con un proprio flusso logico.
>> - **Agente**: entità autonoma con un proprio flusso di controllo, che svolge dei task. Percepisce l'ambiente con i sensori (percezione), decide e agisce sull'ambiente con gli attuatori (azione). Ha comportamento reattivo e proattivo, e porta a una progettazione **orientata ai task**.
>> - Un lavoro complesso si scompone in **task**, ognuno descrivibile con una macchina a stati. Più agenti che interagiscono formano un **sistema multi-agente** (smart home, smart city, IoT).
